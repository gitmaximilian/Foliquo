# Foliquo Community Improvements: Implementation Status

This document tracks implementation separately from automated verification and external evidence. The detailed scope and acceptance criteria are in the private handoff plan dated 30 October 2026.

## Baseline

- Starting commit: `1bbf22f` (`docs: record v0.11.11 distribution verification`).
- Starting branch: `codex/release-validation-0.11.11`, tracking the matching origin branch.
- Initial worktree: clean; no pre-existing user changes.
- Repository instructions: Node.js 22+, loopback-only service, browser/CLI and Tauri retained, English repository documentation, fictional test data, preserve PDF/Word behavior and human-review boundary.
- Baseline defect confirmed by source inspection: `lib/memory.mjs` exposes `matchedLineCount` and deliberately withholds private example text; `dist/workflow.js` dereferenced `ref.matches` and rendered `ref.translation`.
- Baseline storage risk confirmed by source inspection: successful queue entries can have results evicted and marked `expired` over the 160 MiB in-memory threshold; workspace persistence remains one encrypted JSON file capped at 256 MiB.
- No customer documents or personal workspace data were used.

### P02 follow-up: binary-safe fingerprints and real-file scale run

- Commit: `07b094e` (`perf: hash archived job state without binary expansion`).

- Implementation in progress: JobStore now hashes new job state incrementally, including binary payloads, instead of first expanding a Buffer through `JSON.stringify(Buffer)` into a numeric array. New index entries identify the fingerprint format; legacy JSON fingerprints are verified once and upgraded in memory while their encrypted record remains reusable. Hydrated binary sidecars now return Buffers directly rather than Buffer-shaped JSON objects.

#### Local recovery point implementation in progress (commit `122f28a`)

- New `lib/recovery-points.mjs` keeps committed workspace files in a private `.recovery-points/` directory. Snapshot files are already AES-256-GCM encrypted; the snapshot manifest is authenticated with the local workspace key. Snapshot file hashes and lengths are verified before recovery.
- Unchanged encrypted files use hardlinks where supported; filesystems that reject hardlinks use private copies. Retention keeps at most seven points and enforces a 4 GiB unique-file storage budget. Automatic snapshots are limited to one per 24 hours; migration and restore create explicit points.
- Startup can restore the newest fully verified point when the workspace key is missing/invalid, the active encrypted manifest is missing or cannot be decrypted/parsed, the authenticated JobStore index is damaged/missing for a committed generation, or an archived record/sidecar being loaded during startup is damaged. Runtime access to a damaged lazy record or object now restores and reloads the last verified point for review and streamed-export requests; concurrent HTTP requests wait until the recovery attempt finishes. A successfully authenticated but schema-invalid current workspace is deliberately not rolled back.
- The storage settings view explains the point count/budget and that same-disk points do not replace an external backup; it also reports checkpoint creation errors and an automatic recovery date.
- Runtime recovery follow-up: `Workspace.recoverFromLatest()` restores and reopens the verified generation in the existing Workspace object. Server routes retry once after recoverable JobStore record/sidecar corruption, and in-flight HTTP work is held while the recovery transaction runs. Errors from lazy metadata reads and authenticated object streams now expose the same recoverable corruption code.
