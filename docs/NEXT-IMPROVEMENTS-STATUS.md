# Foliquo Community Improvements: Implementation Status

This document tracks implementation separately from automated verification and external evidence. The detailed scope and acceptance criteria are in the private handoff plan dated 30 October 2026.

## Baseline

- Starting commit: `1bbf22f` (`docs: record v0.11.11 distribution verification`).
- Starting branch: `codex/release-validation-0.11.11`, tracking the matching origin branch.
- Initial worktree: clean; no pre-existing user changes.
- Repository instructions: Node.js 22+, loopback-only service, browser/CLI and Tauri retained, English repository documentation, fictional test data, preserve PDF/Word behavior and human-review boundary.
- Baseline defect confirmed by source inspection: `lib/memory.mjs` exposes `matchedLineCount` and deliberately withholds private example text; `dist/workflow.js` dereferenced `ref.matches` and rendered `ref.translation`.
- Baseline storage risk confirmed by source inspection: successful queue entries can have results evicted and marked `expired` over the 160 MiB in-memory threshold; workspace persistence remains one encrypted JSON file capped at 256 MiB.
- No customer documents or personal workspace data were used.

### P02 follow-up: streamed backup download

- Commit: `a64aa67` (`perf: stream backup downloads to selected files`).
- Implementation: `dist/workspace.js` now uses `showSaveFilePicker()` and pipes the encrypted backup response body into the selected file without first creating a full Blob. If the File System Access API is unavailable, the existing Blob download remains as a compatibility fallback. Cancelling the save dialog exits before making the backup request.
- Browser coverage: `tests/browser/backup-stream.spec.mjs` exercises the native-save path with a simulated writable stream and verifies the encrypted `TOCRBACK1` bytes, filename, and password clearing. A second browser case disables the picker and verifies the fallback download bytes and filename; a third confirms cancellation makes no request and preserves the passphrase.
- Verification: `npm test` 214/214; `npm run test:browser` 4/4; `npm run acceptance` 12/12; `npm run benchmark` 3 offline cases, 0 regressions; `npm run demo:build` passed and generated demo assets were restored. `git diff --check` and `node --check` passed for changed JavaScript.
- Data impact: none; tests use a fresh temporary workspace and fictional backup contents.
- Remaining P02 work: legacy JSON/Base64 restore still buffers the complete request, and authenticated TOCRBACK1 validation still materializes decrypted JSON; the 256 MiB cap, large-archive stress, crash/ENOSPC and cross-platform migration evidence remain open.

### P02 follow-up: staged raw backup restore

- Commit: `ae81a25` (`perf: stage raw backup restores to private disk`).
- Implementation: the raw `application/octet-stream` restore route now pipes request bytes to a uniquely created private staging directory (`0700`) and file (`0600`) with backpressure and an explicit 256 MiB archive cap. The staged file is removed after success, authentication failure, or interrupted upload. The current TOCRBACK1 format is then read once into memory for authenticated decryption and JSON/schema validation; the larger streaming archive/record redesign remains future P02 work. The legacy JSON/Base64 endpoint remains supported.
- Restore safety: a failed workspace-manifest write rolls the in-memory workspace reference and replace-all state back to the pre-restore values; the JobStore transaction handles its own index/object rollback.
- Tests: streamed restore success; invalid passphrase and interrupted upload leave no staging files and preserve active data; an HTTP-level failed manifest write keeps the previous workspace active.
- Verification after the implementation: `npm test` 216/216; `npm run test:browser` 5/5; `npm run acceptance` 12/12; `npm run benchmark` 3 offline cases, 0 regressions; `npm run demo:build` passed and generated demo assets were restored. `node --check` and `git diff --check` passed.
- Data impact: tests use only temporary workspaces and fictional content.

### P02 follow-up: bounded archived-job read accounting

- Commit: `baf9a3c` (`perf: avoid serializing archived jobs during reads`).
- New encrypted job-index entries now store a SHA-256 digest of the compact externalized record. Reads verify this digest before parsing and hydrating sidecar objects; they no longer re-stringify the fully hydrated job to compare the legacy digest. Old entries without this additive digest retain their prior validation behavior.
- Cache admission now uses a heap-weight estimate that accounts for Buffer bytes, arrays, strings and object fields instead of serializing the whole job solely to estimate cache size. Queue cache limits remain enforced.
- Regression test constructs a 256 KiB fictional source object, intercepts `JSON.stringify` to fail if the hydrated full job is serialized, confirms digest verification and bounded caching, then rejects a mismatched record digest.
- Verification after this change: `npm test` 217/217; `npm run test:browser` 5/5; `npm run acceptance` 12/12; `npm run benchmark` 3 offline cases, 0 regressions; `npm run demo:build` passed and generated demo assets were restored. `node --check` and `git diff --check` passed.
- Remaining: callers still request and hydrate full job data when opening an archived job; the 1 GiB archive/RAM acceptance and legacy-index fallback coverage remain to be expanded.

### P02 follow-up: binary-safe fingerprints and real-file scale run

- Commit: `07b094e` (`perf: hash archived job state without binary expansion`).

- Implementation in progress: JobStore now hashes new job state incrementally, including binary payloads, instead of first expanding a Buffer through `JSON.stringify(Buffer)` into a numeric array. New index entries identify the fingerprint format; legacy JSON fingerprints are verified once and upgraded in memory while their encrypted record remains reusable. Hydrated binary sidecars now return Buffers directly rather than Buffer-shaped JSON objects.
- Regression coverage: a 1 MiB fictional binary record proves writes and unchanged-record detection do not JSON-stringify the original Buffer, equivalent bytes reuse the record, and a changed byte replaces it. A legacy-index case verifies its prior fingerprint once and checks the compatibility upgrade. Existing schema-1 migration, backup, restore, and workspace tests now assert real Buffer rehydration.
- Scale evidence: `npm run test:storage` created 100 encrypted records with 11 MiB each (1,153,433,600 total bytes) in a fresh temporary directory, reopened the JobStore, verified every rehydrated payload by SHA-256, and exported each payload through a real file before verifying it again. The test removed its temporary directory. This establishes file-backed 100-job/>1 GiB integrity, not a peak-RAM measurement.
- Verification: `node --test tests/job-store.test.mjs tests/workspace.test.mjs` passed 34/34; `npm run test:storage` passed; `npm test` passed 219/219; `npm run test:browser` passed 5/5; `npm run benchmark` reported 3 offline cases and 0 regressions; `npm run acceptance` passed 12/12; `npm run demo:build` passed and its generated tracked assets were restored; `node --check` passed for `lib/job-store.mjs` and `scripts/storage-scale.mjs`; `git diff --check` passed.
- Data impact: only fictitious records and random test keys in temporary directories; no user workspace was opened. The test command adds no retained test archive.
- Remaining: profile peak RAM for valid >160 MiB PDF validation and HTTP retrieval; run crash-point, ENOSPC, permission, and cross-platform migration cases. The portable backup format remains capped at 256 MiB and restore still materializes decrypted JSON; legacy Base64 restore and incomplete-artifact fallback still buffer data. P02/P03 therefore remain implementing.

### P02 follow-up: archive-index idle memory measurement

### P02 follow-up: very large result-sidecar restart and export

- Core fix commit: `3814fca` (`fix: validate large archived exports in chunks`). HTTP restart regression commit: `bce019a` (`test: verify large archived PDF download after restart`).

- The first >160 MiB acceptance run exposed a stack overflow in one-shot Base64 RegExp validation for archived PDF/Word strings. `lib/job-store.mjs` now validates Base64 in bounded 64 KiB chunks while preserving padding rules, then decodes it incrementally into the authenticated object store.
- Expanded `npm run test:storage` with a 161 MiB binary fixture stored in the `result.pdf` sidecar. It initializes a fresh JobStore from disk, retrieves the owner-scoped object, streams decrypted bytes to an export file, and verifies its SHA-256 digest. This complements the 100-job, 1,100 MiB source-object restart/export case. A separate integration regression covers a valid 161 MiB PDF through server/workspace restart and HTTP download.
- Verification: `npm run test:storage` passed with 100 jobs / 1,153,433,600 source bytes plus a 168,820,736-byte result fixture exported byte-for-byte. This fixture verifies persistence and streaming of the large result object; it is not itself a valid PDF. The separate HTTP integration regression uses a valid 161 MiB PDF and verifies post-restart PDF parsing plus the streamed user-facing download endpoint.
- Remaining: profile/limit peak RAM for large PDF validation and export; complete crash-point, ENOSPC, permission, and platform migration cases; redesign large portable backup/restore while retaining `TOCRBACK1` import compatibility.

### P02 follow-up: process-exit transaction recovery

- A subprocess regression now exits immediately after the sidecar object write, after the replacement record write, and after atomic index publication. Each fixture is reopened by a new JobStore instance. The first two states retain the complete previous job; the post-index state contains the complete new job. The test compares both text and binary payload to ensure generations are never mixed.
- Verification: targeted subprocess test passed; full `npm test` passed 221/221. This models process termination at durable commit boundaries; it is not a power-loss/filesystem durability test and does not simulate a kill during an individual file write.
- Remaining: test a kill during partial secure-object writes and cleanup/recovery of stale staging files; exercise ENOSPC, permissions, and migrations on supported platforms.
