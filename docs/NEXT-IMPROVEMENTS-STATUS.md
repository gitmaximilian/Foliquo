# Foliquo Community Improvements: Implementation Status

This document tracks implementation separately from automated verification and external evidence. The detailed scope and acceptance criteria are in the private handoff plan dated 30 October 2026.

## Baseline

- Starting commit: `1bbf22f` (`docs: record v0.11.11 distribution verification`).
- Starting branch: `codex/release-validation-0.11.11`, tracking the matching origin branch.
- Initial worktree: clean; no pre-existing user changes.
- Repository instructions: Node.js 22+, loopback-only service, browser/CLI and Tauri retained, English repository documentation, fictional test data, preserve PDF/Word behavior and human-review boundary.
- Baseline defect confirmed by source inspection: `lib/memory.mjs` exposes `matchedLineCount` and deliberately withholds private example text; `dist/workflow.js` dereferenced `ref.matches` and rendered `ref.translation`.
- Baseline storage risk confirmed by source inspection: successful queue entries can have results evicted and marked `expired` over the 160 MiB in-memory threshold; workspace persistence remains one encrypted JSON file capped at 256 MiB.
- No customer documents or personal workspace data were used.

### P02 follow-up: staged raw backup restore

- Commit: `ae81a25` (`perf: stage raw backup restores to private disk`).
- Implementation: the raw `application/octet-stream` restore route now pipes request bytes to a uniquely created private staging directory (`0700`) and file (`0600`) with backpressure and an explicit 256 MiB archive cap. The staged file is removed after success, authentication failure, or interrupted upload. The current TOCRBACK1 format is then read once into memory for authenticated decryption and JSON/schema validation; the larger streaming archive/record redesign remains future P02 work. The legacy JSON/Base64 endpoint remains supported.
- Restore safety: a failed workspace-manifest write rolls the in-memory workspace reference and replace-all state back to the pre-restore values; the JobStore transaction handles its own index/object rollback.
- Tests: streamed restore success; invalid passphrase and interrupted upload leave no staging files and preserve active data; an HTTP-level failed manifest write keeps the previous workspace active.
- Verification after the implementation: `npm test` 216/216; `npm run test:browser` 5/5; `npm run acceptance` 12/12; `npm run benchmark` 3 offline cases, 0 regressions; `npm run demo:build` passed and generated demo assets were restored. `node --check` and `git diff --check` passed.
- Data impact: tests use only temporary workspaces and fictional content.

### P02 follow-up: bounded archived-job read accounting

- Commit: `baf9a3c` (`perf: avoid serializing archived jobs during reads`).
- New encrypted job-index entries now store a SHA-256 digest of the compact externalized record. Reads verify this digest before parsing and hydrating sidecar objects; they no longer re-stringify the fully hydrated job to compare the legacy digest. Old entries without this additive digest retain their prior validation behavior.
- Cache admission now uses a heap-weight estimate that accounts for Buffer bytes, arrays, strings and object fields instead of serializing the whole job solely to estimate cache size. Queue cache limits remain enforced.
- Regression test constructs a 256 KiB fictional source object, intercepts `JSON.stringify` to fail if the hydrated full job is serialized, confirms digest verification and bounded caching, then rejects a mismatched record digest.
- Verification after this change: `npm test` 217/217; `npm run test:browser` 5/5; `npm run acceptance` 12/12; `npm run benchmark` 3 offline cases, 0 regressions; `npm run demo:build` passed and generated demo assets were restored. `node --check` and `git diff --check` passed.
- Remaining: callers still request and hydrate full job data when opening an archived job; the 1 GiB archive/RAM acceptance and legacy-index fallback coverage remain to be expanded.

### P02 follow-up: stream large legacy translation text into encrypted job objects, 31 October 2026

- The TOCRBACK1 parser now decodes `result.text` incrementally to a private staging sidecar once the encoded JSON string exceeds 1 MiB. The staged job JSON is compacted by streaming the original byte ranges around that text value and replacing it with an empty placeholder; this keeps later restore/save from reparsing or serializing the giant translation. During save, JobStore encrypts the staged UTF-8 file directly as its authenticated working object. The streamed state fingerprint preserves the same value as the ordinary in-memory fingerprint, and a later commit reuses the same record. Staging remains private and is removed after commit or rejected restore.
